# Shop Ledger

A mobile-first React shop ledger: payment in/out, Sale, Purchase, Bhara (transport/delivery), Expense, Cash/Online/Cheque, date-range filtering and A4 printing. No login or cheque-status tracking. Party accounts and invoices are available on the feature branch. INR is the initial currency; new transaction dates and report periods use Asia/Kolkata.

This build is branded for Royal Furnitures. Its logo, shop name, tagline, address and phone appear in the app and print reports. The address and phone are included in this public static site and its source repository. New transaction dates, report periods and timezone labels use Asia/Kolkata; amounts remain INR. Per-browser Shop & preferences can still override the report details.

## Run locally

Use npm to install and start the app:

```sh
npm install
npm run dev
```

The project includes Node 22 as a development dependency. After `npm install`, npm scripts automatically use this local version, even if your system Node is 18. A first install with Node 18 may show an engine warning before the local runtime is installed. You do not need to change your system Node. If you prefer a version manager, `.nvmrc` also selects Node 22.

`npm test` runs business-rule and backend tests. `npm run build` produces `dist/`. Only React and React DOM are runtime dependencies; Vite handles development and builds. CSS uses optional Google Fonts with local fallbacks.

## Connect your Google Sheet

1. Create a private Google Sheet. Set its timezone under File → Settings to your shop timezone (for example Asia/Kolkata). Use the same timezone on the devices entering payments.
2. Open the app’s Settings. Download or copy Code.gs (the exact `google-apps-script/Code.gs` included in this release). Open Extensions → Apps Script in your Sheet and paste it into the editor.
3. Run `setup` once and authorize it. It creates `Transactions` and `Report` tabs and stores the spreadsheet ID in Script Properties.
4. Deploy → New deployment → Web app. Execute as yourself; allow access to Anyone. Copy the deployed URL ending in `/exec`.
5. In Settings, paste the deployed URL and choose **Test & save connection**. There is no default endpoint. The app saves the link in this browser only after a successful response containing ledger records, and reconnects when you return. Settings shows the saved URL, connection status, last successful check, deployed backend version, and included script version. Older scripts show “Unknown” until updated. The URL is generated by Google during deployment, not by the app.
6. Record a small test payment. Confirm the row appears in the sheet, refresh the app, and print a report. Confirm the deployment works from your actual GitHub Pages URL and mobile browser before using real records.

When updating backend code, edit the existing deployment to use a new version. A development `/dev` URL will not work. Workspace accounts may prohibit anonymous web apps; an administrator must allow this or you need a different backend.

**Access model:** No login is required. Anyone with the endpoint can read, add and delete records through the script. No shop endpoint is hardcoded or included in the build. Each browser stores its own connection in localStorage. This keeps private connection choices out of the shared source, but is not authentication: anyone who obtains a URL can still call it. Keep the underlying sheet private. Removing Firebase in this project does not delete any Firebase project you may have created. If you deployed the authenticated backend, replace it with the current Code.gs and deploy a new version to restore direct access. Old Firebase Script Properties are unused and may be removed; keep SPREADSHEET_ID.

## Sheet schema and future features

The `Transactions` tab is the source of truth. Never rename existing headers or reuse their meaning. Column order is not significant: backend reads and writes by header name. Add new columns to `HEADERS`; initialization appends only missing headers, preserving old rows and unknown columns. Blank fields in old records mean “not recorded”; new readers should supply defaults. Give each future incompatible schema a new `schemaVersion` and add an explicit reader/validator for it before writing it. Existing unused `Reconciliations` tabs from earlier versions are left untouched.

| Field | Meaning |
|---|---|
| id | Permanent UUID; retries with the same content are idempotent |
| schemaVersion | Version 1 for current records |
| transactionDate, transactionTime, timezone | Local business date, 24-hour time, and device timezone |
| direction | `in` or `out`, independently of category |
| category | Sale, Purchase, Bhara, Expense |
| method | Cash, Online, Cheque |
| amountMinor, currency | Integer paise and INR; avoids decimal rounding in totals |
| party, notes | Optional text |
| chequeDate | Date cheque was given; mandatory for cheques |
| createdAt | Server-recorded UTC creation timestamp |
| metadata | Reserved JSON object for future optional fields |
| recordType | `payment` for existing business transactions; `transfer` for cash/online balance exchanges |
| cashReceivedMinor, cashChangeMinor, onlineChangeMinor | Sale cash tender and any cash or online change returned, stored as integer paise |
| fromMethod, toMethod | For `transfer` rows, the balance account money leaves and enters; currently Cash or Online |

New settlement and transfer fields were added at the end of the sheet schema. Existing rows keep their values and are interpreted as ordinary payments. A cash Sale can record the amount physically received, calculate the total change due, and split returned change between cash and online. Change defaults to cash; adjusting either return amount updates the other to the remaining change. A separate Cash ↔ Online exchange records balance adjustments that are not revenue or expense. These settlement and exchange features require Apps Script backend 1.4.0; replace Code.gs and deploy a New version before saving them. Cashflow adjustment records require backend 1.6.0. They store expected, counted, and signed difference amounts in new columns appended to Transactions, preserving all earlier rows and headers; they affect current cash/online balances only and are excluded from income, expense, and category reports. The app blocks these advanced records against older deployments while ordinary payments continue to work.

Future invoices, customers, or edit history should use separate tabs linked by stable IDs. Avoid changing existing rows to accommodate new features. Each transaction has a Delete button with confirmation. Deletion sets a server-generated `deletedAt` timestamp; the row remains recoverable in Sheets but is excluded from app reads and regenerated reports. Blank `deletedAt` values on older rows mean active. Delete retries are idempotent, and a deleted ID cannot be recreated. History includes Edit: it loads the original values into the payment form and preserves the date/time. Save changes updates the same row and keeps the ID, creation timestamp, metadata and unknown columns. Edits add updatedAt, revision and lastEditId columns; older records use revision zero. Conflicting edits from another device are rejected and must be reloaded. Network retries are idempotent. It validates writes, locks concurrent writes, neutralizes spreadsheet formula inputs and checks duplicate IDs. Both frontend and backend validation must be extended when introducing categories or methods.

## Reports and save behavior

The app defaults to this calendar month. All summary cards and print results follow the active period, category, method and search filters. Category totals show gross recorded amounts; net cash flow is payment in minus payment out, not profit or cash on hand. Cheques are included immediately as recorded payments because cheque status is excluded.

Print A4 report opens the browser print dialog. Choose A4 (or Save as PDF) and disable browser headers/footers if desired. Printed output identifies cached data when the latest read has not been confirmed.

In Google Sheets, set start/end dates in Report!B2:B3, then select **Shop Ledger → Refresh report**. This rebuilds category totals without modifying transactions. The tab is an explicit snapshot, not automatically refreshed after each payment; its generation timestamp is shown. You can optionally add a time-driven Apps Script trigger for `refreshReport`.

If report-date validation fails, replace your Apps Script code with the latest `Code.gs`, save, and run `resetReportDates`. This resets only the report period to the current month in the sheet's timezone and refreshes the report; transaction rows are preserved. For custom periods, use actual Sheet date cells or unambiguous `YYYY-MM-DD` text in B2 and B3, with start on or before end. Rerunning `setup` fills missing date cells while preserving existing selections.

A payment is successful only after the server confirms its ID. Before sending, the app saves the pending record on the device. If a request fails or times out, Retry uses the same ID and payload, including after reload. Resolve a pending record before adding another, switching endpoints, or disconnecting. New pending records remember their original endpoint and cannot be retried against another sheet. Legacy pending records without a saved endpoint require confirmation of their original destination before retrying. Do not clear browser storage while a record is pending. Loaded records remain in memory only. A new visit requires a connection to Google Sheets. Pending payments are stored on this device for retry recovery. Refresh retrieves records added from other devices.

The app fetches the full sheet for this initial shop-scale version. For very large ledgers, add server-side date filtering and pagination behind the same API without changing historical rows. Apps Script quotas apply. A live Google deployment is needed to verify cross-origin requests, account permissions and end-to-end writes; those cannot be validated with local tests alone. Apps Script uses [web app handlers](https://developers.google.com/apps-script/guides/web) and [ContentService](https://developers.google.com/apps-script/reference/content/content-service).

To enable deletion on an existing installation, replace Apps Script code with the latest `Code.gs` and update the deployment to a new version. The `deletedAt` column is appended automatically. Refresh the Report tab after deletion to regenerate its snapshot.

Pending saves from the former signed-in version (`rf.pending.<user ID>`) are retained in browser storage but are not automatically merged into the anonymous queue. If you used that version and had an unconfirmed payment, check its ID against the sheet before re-entering it.

Live account authorization and deployment must be performed by each sheet owner.

## Shop preferences, appearance, exports, and recovery

Open Settings → Shop & preferences. Shop name, address, phone, preferred category/method, light/dark appearance, larger text, and print notes/contact controls are saved per connection in this browser. Preferences do not synchronize between devices. They apply after Save preferences; existing drafts and edits are preserved. Defaults apply on startup and New entry, while a successful payment keeps the last selection for repeated entries.

Shop name is shown in the app and always on printed reports. Address and phone appear on app-generated A4 reports when Print contact is enabled; notes are independently optional. Dark mode and larger screen text do not change the print stylesheet. These preferences do not modify the Google Sheet's Report tab.

CSV export loads fresh active records for the selected inclusive date range (initialized from the current report period), independent of category/search/method filters. It includes all payment fields, original IDs and timestamps, quotes multiline text, exports INR amounts as decimal rupees, and protects spreadsheet programs from formula-like text. An empty period exports headers only. CSV is an export format, not an implemented import/restore feature.

Deleted transactions are loaded on demand from Settings. Restore preserves the original row, ID, amount, dates and other details, removes the deletion marker and records restoredAt. Retrying restoration is safe. Delete/restore increment revision so older edits cannot overwrite a changed record. A payment deleted again after restoration must be reloaded before restoring again. Refresh the Sheet Report tab to rebuild its snapshot after a restore.

The Dashboard shows all-time cash in hand and online balances, calculated as valid inflows minus outflows across recorded transactions. Cash/online exchanges and change returned on cash sales are included. The balance cards are independent of the selected report period; payment summaries and the transaction list still follow that period.

Recovery, editing, cash change, and balance exchanges require Code.gs 1.4.0. Cashflow adjustments require Code.gs 1.6.0. Download the latest Code.gs from Settings → Google Sheets setup, replace your Apps Script code, save, and deploy a New version of the existing deployment. Existing transaction rows are retained unchanged. The app remains unauthenticated; anyone with a shop's endpoint can also restore its records.

### Accounting rules

A party balance is opening balance + issued sales invoices − issued purchase invoices − payments received + payments made. Positive means the party owes the shop; negative means the shop owes the party (including advances). One party can be both customer and supplier; this first version shows its net balance. Payments select a stable party ID and are not allocated to invoices. Individual invoices have no paid/unpaid status. Cheques affect balances immediately, consistently with the existing payment ledger.

Opening balance is the amount immediately before entries on its effective date. Linked payments and invoices cannot predate that date. Party name, phone and address can be edited with revision checks; opening date and balance are immutable in this release. Old name-only payments remain unlinked. Linking an old payment explicitly through Edit changes the party balance, so do not include that same payment in the opening amount. Parties are not deleted through the UI.

Invoices are issued independently of payment transactions and never affect cash/online balances. Invoice numbers are assigned on the Sheet when issued: RF-S-000001 for sales and RF-P-000001 for purchases, with separate increasing sequences. The server scans existing numbers under its write lock, including cancelled invoices, so concurrent devices cannot issue the same number. Existing invoice numbers remain unchanged. Draft invoices live only in this browser, per endpoint. Issued invoices can be edited with backend 1.9.0: items, quantities, rates, discounts, internal costs, date and notes can change. Invoice number, party and sale/purchase type stay fixed. Cancel with a reason for a voided invoice; cancelled invoices cannot be edited. Cancellation preserves the invoice and items but removes its effect on current balances and invoice reports; related party payments remain. Reports reflect current cancellation status, not a historical as-of audit of when cancellation occurred.

Amounts are integer paise; quantities support three decimal places using integer thousandths. Each line total is quantity × unit rate, rounded to paise, minus its whole-line discount. Sales invoices optionally snapshot internal unit costs. Gross profit is invoice total minus rounded item costs; all costs must be supplied for an invoice to contribute to profit. Missing costs are counted and disclosed instead of treated as zero. This is gross profit, not net profit: operating expenses are separate. This release does not calculate GST/taxes, inventory cost allocation, returns or credit notes, or produce statutory tax invoices.

Dashboard invoice figures use invoice dates and the selected date period, independent of payment category/method/search filters. Payment cards retain their original meanings and are labelled as payment categories. Never add invoice sales and Sale-category receipts together. Party balances use all confirmed records and show a separate receivable/payable total based on each party's net position. Refresh invoice figures to retrieve changes made on other devices; failed reads retain the previous snapshot with a warning.

### Additive Sheet schema and recovery

Existing `Transactions` records, schema version 1, IDs, headers and unknown columns are preserved. `partyId` is appended as an optional column. Blank means no party account; names are never matched automatically. Old clients cannot edit linked payments without explicitly understanding `partyId`.

New tabs are created by `setup` (or on first account request):

- `Parties`: permanent ID, schema version, name, phone, address, signed opening balance in paise, opening date, creation/update timestamps, revision, last edit ID and reserved archive timestamp.
- `Invoices`: permanent ID, schema version, party ID, party contact snapshot, sales/purchase type, invoice number/date, notes, INR totals, optional internal cost total, item count, issued/cancelled status and cancellation details.
- `InvoiceItems`: deterministic ID, parent invoice ID, description, integer quantity thousandths, rate, line discount, line total, optional unit cost and line cost, all amounts in paise.

Sheet access uses headers rather than fixed column positions. Writes run under the script lock. Invoice totals are recalculated on the backend. Items are staged before committing the invoice header. Account reads acquire the same lock and only expose items through a complete invoice header. An interrupted write can leave orphan staged items; retrying the same invoice ID completes it without duplicating lines. Do not manually delete staging rows during recovery. Account reads reject incomplete/corrupt invoices instead of publishing partial balances.

Party/invoice requests are stored durably in `rf.accounts.pending` with their original endpoint and payload before sending. A timeout leaves a retryable request across reloads, and changing connection is blocked until resolved. Backend rejections can be discarded to correct a draft; ambiguous network failures require retry. Issuing an invoice stores its request locally and closes the popup immediately. Upload continues in the background; a status banner shows the assigned RF number after confirmation. Parties created from invoice entry save locally and return to the invoice immediately. A durable queue uploads each new party before its dependent invoices. Existing saved single requests are migrated into the queue. Multiple new invoices can be entered while uploads continue. Saving an invoice opens its local preview immediately; printing requires a confirmed RF number. Queued requests resume on reopening the app; requests with a saved network failure retry on restored connectivity or Retry upload. Backend rejections require review. Party balances and invoice totals include only Sheet-confirmed invoices. Rejected invoice requests can be restored as a draft for correction. Browser storage must not be cleared with an unconfirmed request. Invoice drafts are stored separately as `rf.invoiceDraft.<endpoint>`.

The existing Google Sheet `Report` remains a payment report. Party statements are generated by the app: compact ledger or detailed ledger including invoice lines, with an opening balance carried forward and a closing balance. Both refresh confirmed records before printing and are blocked while payments are queued. Internal costs and profit are never rendered in statement output. Cancelled invoices are retained in the invoice register but excluded from statements.

### Test acceptance checklist

1. Confirm first launch opens setup and that closing/reopening Settings works.
2. Connect only the copied test Sheet and verify the original Sheet remains unchanged.
3. Add a party with zero opening balance dated before the first test invoice.
4. Issue a ₹20,000 sales invoice with ₹14,000 total cost. Expect ₹20,000 receivable and ₹6,000 gross profit; cash stays unchanged.
5. Receive ₹5,000 using that party. Expect ₹15,000 receivable and ₹5,000 more cash; invoice sales and profit stay unchanged.
6. Record a ₹30,000 purchase invoice for a supplier and pay ₹10,000. Expect ₹20,000 payable.
7. Check an advance payment, a nonzero opening balance, fractional quantities, discounts and an invoice with missing costs.
8. Print compact and detailed party statements; verify opening/closing balances, invoice items only in detailed format, and no internal costs.
9. Cancel an invoice and verify payments remain, the balance changes, and the cancelled document remains in Sheets.
10. Interrupt an invoice upload, reload, and retry. Verify only one invoice and its original items exist.
11. Recheck old transaction totals, cash change, exchanges, adjustments, editing and deletion/restoration before merging.

Automated tests exercise calculations, schema preservation, validation, duplicate retries, interruption recovery, snapshots and cancellation using an in-memory Apps Script Sheet harness. Live Google authorization, deployment and cross-origin requests must also be tested against the copied Sheet.


### Faster party loading (backend 1.7.1)

Party/invoice snapshots are cached per Sheet endpoint in IndexedDB. Returning visits show the saved snapshot while one shared request refreshes it; the page displays its last-updated time. Switching between account views reuses recently confirmed data for up to one minute. Payment uploads refresh accounts once the queue drains, and print actions require a fresh read. Backend 1.8.1 returns confirmed party/invoice records with write acknowledgements, so saving no longer requires a second full-Sheet fetch. Supported older deployments fall back to a post-operation read. Cache contents are never accepted as a fresh print confirmation.

The app no longer fetches all account records whenever the local payment array changes. Concurrent background account reads share one request. Backend 1.8.0 retains the 1.7.1 improvement that reads each account tab as one range, avoids formatting or schema writes during reads, and indexes invoice items/party references once. The read lock is retained to avoid exposing incomplete invoices. Deploy this code as a new version of the test backend to enable automatic invoice numbering.

### Business overview, sync status and invoice corrections (backend 1.10.0)

The dashboard separates net invoiced sales/purchases, payments received/made, all-date party receivables/payables, gross profit and recorded operating expenses. Net invoice figures include issued credit/debit notes dated in the selected period. Gross profit uses entered sales costs and cost corrections; it remains hidden until **Show profit** is clicked. Missing costs are excluded from the partial gross-profit figure and make **Profit after recorded expenses** unavailable. Operating expenses are Expense and Bhara payments out less refunds in; purchase payments are not subtracted a second time. These are figures based on recorded activity, rather than a complete accrual accounting profit report. Pending invoice/note uploads and queued payment changes are excluded from the overview until confirmed.

**Save and sync status** combines payment, party, invoice and correction-note queues, showing Saved locally, Uploading, Synced, Offline or Needs attention. Expand it for pending-record details and refresh controls. Failed requests remain on the original device, with retry/recovery buttons. A saved browser snapshot is labelled as such; it is not presented as a fresh Sheet confirmation.

To correct an issued invoice, open it and click **Create credit / debit note**. A credit reduces that invoice's value; a debit increases it. For sales this reduces/increases the receivable; for purchases it reduces/increases the payable. Enter a date, amount and reason. Price corrections leave sales costs unchanged; goods/cost corrections allow an optional manual cost amount, with blank meaning unknown. No inventory or stock functionality is added. Notes save locally and upload in the background, receive RF-CN/RF-DN numbers on confirmation, appear in History and party statements, and can be opened and printed. Internal cost corrections are never printed. Refund/payment shortcuts open a separate party-level payment; they never record money automatically or allocate a payment to an invoice.

Notes do not rewrite invoice or payment rows. An invoice that has any correction notes is protected from further editing to preserve the referenced document, even when a note was cancelled. Delete Invoice (backend 1.11.0) removes the invoice and its notes from the active ledger while preserving the underlying rows. Edit a note to correct its amount, date, reason or cost treatment, or delete a mistaken note with a reason (backend 1.12.0). Previous versions and deleted rows stay in the Sheet. Cancellation remains available. Dependent credit/cost corrections must be cancelled first if cancelling their debit would make the remaining value/cost negative. Rejected note uploads can be discarded only after checking the Sheet, then restored in the form for correction. Lost confirmations retry the same note ID and do not create another note or number.

Deploy the bundled `google-apps-script/Code.gs` **1.11.0** to the copied TEST Sheet first: paste the updated script, run `setup()`, then **Deploy → Manage deployments → Edit → New version → Deploy**. Keep the existing deployment URL and refresh the app. Setup adds the `InvoiceNotes` tab and missing headers; existing invoice, item, party and payment data is preserved. Older backends continue supporting their existing features; note creation stays disabled until the account response confirms 1.10.0 or newer. The UI does not deploy a script or change the real Sheet on its own.

`InvoiceNotes` stores `id`, `schemaVersion`, `invoiceId`, `invoiceNumber`, `invoiceRevision`, party/contact snapshots, `invoiceType`, note `type`, `noteNumber`, `noteDate`, `reason`, `effect`, `amountMinor`, `costAdjustmentMinor`, `currency`, `status`, `createdAt`, cancellation date/reason and `revision`. Amounts use integer paise. The server assigns the note number while holding the script lock, validates the original revision and cumulative amount/cost limits, and preserves previous versions in InvoiceNoteHistory and retains cancellation/deletion metadata. Legacy Sheets without this tab read as having no notes.

Credit-note and supplier-credit conventions were checked against [Zoho Books credit notes](https://www.zoho.com/en-sg/books/help/credit-note/) and [vendor credits](https://www.zoho.com/ca/books/help/vendor-credits/); this app continues to use its simple party-level payment model.


### Invoice/party deletion and explicit party payment choices (backend 1.11.0)

**Delete Invoice** replaces the cancellation button in the invoice popup. It removes the invoice and all its linked correction notes from active History, party balances and dashboard figures; existing payments remain unchanged. The original invoice, item, note and historical edit rows stay in Google Sheets. Invoices use additive optional `deletedAt` and `deleteReason` columns, status `deleted` and an incremented revision. Note rows stay unchanged; a deleted parent's notes are read as inactive. Invoice numbers remain reserved. The server checks the current invoice revision and correction-note revisions before deleting and confirms duplicate delete retries safely.

Open a party and click **Delete Party** to remove an unused party from the directory and pickers. The party row is retained with `archivedAt` and its revision incremented. Parties with issued invoices or active linked payments cannot be deleted. From backend 1.14.1, an opening-only party can be deleted after confirming the receivable/payable removed from active totals; the original opening balance stays in its archived Sheet row and no adjustment/payment is generated. Older backends require an upgrade for nonzero opening balances. Delete linked records first; no payment records are deleted automatically. Archived parties cannot receive new invoices/payments, and deleted payments cannot be restored against an archived party. Existing deleted/cancelled invoice history retains its original party link.

Party-opened payments keep the party selected but start with no direction, category or payment method selected, including those opened from invoice/note shortcuts. Choosing a category does not auto-select a direction in this flow. Choose all three and enter the amount before saving. Ordinary Dashboard payments still use configured defaults, and edits preserve their original selections.

Credit/debit notes are available by opening **Dashboard → Invoices → invoice**, **History → invoice**, or **Parties → party → invoice**, then clicking **Create credit / debit note**. For example, a ₹1,000 sales invoice with a ₹100 credit becomes ₹900; a ₹100 debit increases it to ₹1,100. A credit is useful for returns, discounts and overcharges; a debit records extra charges. The popup includes this explanation, and note creation requires backend 1.10.0 or newer. Invoice and party deletion require the new 1.11.0 deployment. Update the TEST Sheet's script, run `setup()`, deploy a new version, then refresh the app. Deletion is recoverable from retained Sheet rows; this release does not add a restore screen for invoices or parties.

Dashboard shows Cash & Online balances, four Sale/Purchase/Bhara/Expense payment cards for the selected period, a smaller business overview, an expandable payment breakdown and one recent-activity table (latest 15 mixed records). On phones, activity rows use a compact card arrangement with amounts and actions visible without horizontal scrolling. Date/category/search filters apply across record types; payment-method filters affect payments only. Reference, challan number and item-description searches also work with invoice summaries. View and Edit are visible; Print/Delete use the `⋮` menu. Print History renders every filtered record, including those beyond the current page.

The document popup has four type buttons: Sales invoice, Purchase invoice, Credit note and Debit note. Notes support typing and selecting a party, then choosing one of that party’s issued invoices. Opening from a party retains its name; a single eligible invoice is selected automatically. Selecting an invoice directly also fills its party. Changing parties clears the previous invoice selection. Deploy the bundled **1.13.0** script to the copied TEST Sheet, run `setup()`, then deploy a **New version** of the existing web-app deployment and refresh the app. Setup appends the optional `Invoices.challanNumber` column and preserves old rows, unknown columns and previous snapshots. On older backends, existing features still work; the challan field is disabled and drafts containing a challan cannot be issued until the backend supports it.

Backend changes:

- Per-request Sheet/table caches reuse the spreadsheet handle, headers, row values and ID-to-row indexes. These caches are discarded when the request ends, so they cannot serve stale results across requests or after manual Sheet edits.
- Invoice creation and editing stage all missing item rows using one `setValues()` batch, then commit the invoice header only after the existing flush boundary. Retries reuse deterministic item IDs and preserve staged rows, prior snapshots and unknown columns.
- `listAccounts` accepts `{summary:true}` to omit item arrays from list responses. It still validates all items and totals once on the server, so manually damaged item data is not silently accepted in dashboard totals. Summaries retain item-description search text.
- `getInvoices` accepts `{ids:[...]}` (up to 500 distinct IDs per request), returns full validated documents for active records and holds the same consistency lock. The app loads items when opening/editing invoices or preparing detailed statements. Print preparation refreshes the base snapshot and rejects statement preparation if invoice revisions change during detail loading.
- Payments and account summaries share one startup/refresh snapshot on supported backends. Legacy deployments keep their previous read path. Durable payment/account queues continue to overlay pending records locally.
- Responses include numerical `performance` fields: `elapsedMs`, `lockWaitMs`, `reads`, `readMs`, `validationMs`, `writes`, `writeMs`. For execution logs, set the Apps Script property `LEDGER_PERF_LOGGING` to `true`; logs include action/timing/counts without party names, amounts or document contents. Timings measure instrumented operations, not every internal Sheets service call.

History pagination limits rendered rows in the browser. All summary/payment records remain available locally for complete balances and filtering; this release does not paginate authoritative balance calculations or use cross-request caches for financial data.


### Bulk delete from History (backend 1.14.0)

Select individual History rows or **Select all on this page**, navigate between pages to extend the selection, then click **Delete selected**. Changing date/category/search/type/payment-method filters or refreshing the Sheet snapshot clears the selection. Each batch supports up to 100 invoices, payments, exchanges, adjustments or credit/debit notes. Pending uploads and duplicate payment IDs cannot be selected. Finish existing uploads first. One confirmation summarizes the selected record types and asks for a reason.

The app refreshes the Sheet before planning deletion and refuses stale invoice/payment/note revisions or changed invoice-note fingerprints. Selected invoices are deleted first; their attached notes are covered by the existing invoice cascade. Other selected notes are ordered so every intermediate invoice value/cost stays within valid bounds. If no safe order exists, nothing is queued and the app asks you to adjust dependent notes or select the original invoice instead.

All deletion requests are saved together in the durable account queue before uploads start, and processed sequentially using the existing idempotent deletion endpoints. This is not an all-or-nothing Sheet transaction: confirmed deletions remain if a later deletion fails. Processing pauses on failure; **Retry upload** resumes the saved requests without repeating completed records. Sheet rows remain retained, and payment rows keep their original restore behavior. Bulk payment deletions check the expected revision and record the reason in an additive `Transactions.deleteReason` column.

Deploy **1.14.0** to the TEST Sheet, run `setup()`, deploy a new version of the existing web app, then refresh. Existing single-record deletion remains available on its previously supported backend versions; bulk deletion waits for backend 1.14.0.

### Reliability review

Invoice summaries invalidate previously loaded line items on refresh, including direct Sheet edits that keep the original revision. Details are loaded on demand using indexed lookups. Fresh print requests wait for an older detail request to finish, then start a new request; they never reuse that older response. Detail responses must contain exactly the requested invoices with item arrays, and mismatched revisions require a refresh rather than combining inconsistent snapshots.

IndexedDB writes are acknowledged only after their transaction commits. Local account-queue lock waits abort after five seconds if another tab is blocking them, preserving the unsaved form and showing a retry message instead of leaving Save spinning indefinitely. Offline-shell caching tolerates quota/storage failures, keeps successful network responses usable, and returns a readable offline message when no cached page is available. These client fixes require no additional Sheet columns beyond the bundled 1.14.0 backend.

Regression coverage includes delayed invoice detail reads during printing, direct Sheet description edits, incomplete detail responses and retry recovery, aborted browser-storage transactions, unavailable offline storage, and missing cached assets. Browser integration checks use simulated Sheets rather than the connected business Sheet.

### Billing units and grouped sizes (backend 1.15.0)

In **New Invoice / Note**, choose a sales or purchase invoice, enter an item name, then select its **Billing unit**:

- **sq. ft.**: select Feet or Inches and enter length, width and pieces. Inches use `(length × width × pieces) / 144`.
- **running ft.**: length × pieces, or explicitly select **Frame perimeter × pieces** for `2 × (length + width) × pieces`. Inch measurements are divided by 12.
- **kg** or **Nos.**: enter weight/quantity directly, or select **GROUP ITEMS** to add rows with their own quantity and pieces.
- Historical unitless quantities retain their original values; new count invoices use NOS.

Select **GROUP ITEMS**, then use **Add size** to group windows or other measurements under one item description, billing unit, rate and optional CP. Each row can have an optional description. Different units or rates need separate item groups. For example, `36 × 36` inches with 2 pieces, `48 × 34` with 1 piece, and `60 × 48` with 2 pieces total **69.3333 sq. ft.** At ₹350 per sq. ft., the group amount is **₹24,266.67**. The line discount applies once to the whole group. Sales CP uses the same measured quantity; missing CP continues to leave profit uncalculated.

Dimensions/weights accept up to three decimal places; pieces must be whole numbers. Calculations retain exact quantities and round only the final group amount to paise. Displayed quantities use up to four decimal places. Limits are 50 item groups, 100 measurement rows per group and 1,000 measurement rows per invoice. Invoice viewing, editing, draft recovery, printing and detailed party statements retain the measurement breakdown. Alt+B selects billing unit, Alt+L length, Alt+W width, Alt+F pieces and Alt+Z adds a row; Alt+U selects quantity or the first measurement. Shortcuts scroll the field into view.

To enable this feature on the copied TEST Sheet, replace its Apps Script with the bundled **1.15.3** `google-apps-script/Code.gs`, run **setup()**, then **Deploy → Manage deployments → Edit → New version → Deploy**, and refresh the app. The billing-unit selector remains disabled until the connection confirms backend 1.15.0 or newer.

Setup adds optional `billingUnit`, `measurementUnit`, `measurementMode`, and `measurementCount` columns to **InvoiceItems**, plus an **InvoiceMeasurements** tab containing `id`, `invoiceId`, `itemId`, `description`, `lengthMilli`, `widthMilli`, `quantityMilli`, and `pieces`. Existing invoices keep their original quantity and amounts. Measurements use immutable item/version IDs: edits retain older measurement rows and invoice snapshots, and interrupted writes can retry without duplicates. Older clients are refused when editing measured invoices so they cannot silently drop dimensions. Existing party payments and balances continue to use the final invoice amount.

Backend 1.15.1 replaces BigInt literal syntax with `BigInt()` calls so the Apps Script editor can parse the measurement helpers while retaining exact arithmetic and the same Sheet schema. Node/browser execution tests alone did not detect the editor parser restriction.

Invoice views include a **Show profit / Hide profit** toggle for sales invoices. Profit starts hidden on each new view, shows a pending message when any CP is missing, and stays excluded from invoice printing. Entry uses aligned compact fields, places optional size descriptions after dimensions/pieces, and shows group totals in a right-hand summary (above the rows, aligned right, on mobile).

Grouping is opt-in for every billing unit. With grouping off, SQ. FT./RUNNING FT. use a single size and KG/NOS. use a single quantity. Selecting GROUP ITEMS reveals multiple rows and optional descriptions. Ungrouping weights/counts combines their quantities; ungrouping multiple dimension rows requires confirmation to keep only the first size. The count selector shows NOS. only; legacy unitless quantities retain their original saved values. Billing units display uppercase, and typed/pasted item names are converted to uppercase; historical names stay unchanged until edited.

Backend **1.15.2** adds an optional `InvoiceItems.itemNote` column for the extra **Description** field beside the required item name. Descriptions support up to 500 characters and appear in invoice views/prints and detailed party statements, survive draft recovery and versioned edits, and participate in item search. Old clients cannot silently remove a saved description. Deploy the updated Code.gs, run setup(), deploy a new version and refresh; the additional description field is disabled until backend 1.15.2 is confirmed. Existing item names and historical rows are preserved.

### Pre-release review (backend 1.15.3)

Invoice detail requests refuse results that started before a newer snapshot for that invoice, including direct Sheet edits without revision changes. Empty grouped quantities cannot silently bill a hidden quantity: the last row stays available, and older inconsistent drafts recover visible rows. Uppercase item typing retains the cursor position for edits in the middle of a name. Unchanged invoice editors and party/filter lists reuse their previous calculations while typing. Sheet batch staging builds its in-memory index once per batch, and measurement-ID collisions are rejected before a parent invoice commits. No additional Sheet columns are introduced by 1.15.3.

New count invoices on supported backends save NOS. explicitly; older unitless invoices remain unitless when edited. A fresh NOS. selection alone does not mark an otherwise empty form as a resumable draft.
